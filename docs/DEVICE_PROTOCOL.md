# Device protocol

How the Orion apps, the board and the extended brains talk to each other. Everything here is what the firmware in `firmware/components/orion_api`, `orion_prov` and `orion_settings` actually does, and what the app in `lib/core/network` and `lib/features/*/data` actually sends. The mock board in `tool/mock_device` serves the same contract, with the few differences listed at the end.

The board runs the whole voice loop itself: microphone, speech to text, language model, text to speech, speaker. The apps never carry audio. They find the board, pair with it, configure it, watch it, and ask it to do things. On a PC or a phone that holds a live link, the app can also answer the board's turns as an extended brain (see "Board to brain" below and [HARNESS.md](HARNESS.md)).

## At a glance

| What | Where |
|---|---|
| REST and WebSocket | `http://<board>:80`, WebSocket at `ws://<board>/ws` |
| mDNS | host `orion.local`, service `_orion._tcp`, port 80 |
| UDP beacon | broadcast to `255.255.255.255:7332` every 2 s |
| Bluetooth setup | ESP Unified Provisioning over BLE, name `Orion-<last4>` |
| Auth | `X-Orion-Token: <app token>` header, or `?token=` in the query |
| PC and phone brain | the app's tool server, `http://<pc or phone>:7331` (7331 to 7339) |
| Mock board | `http://localhost:8080` |

## Identity

Every board takes its names from the last two bytes of its Wi-Fi station MAC address, in lower case hex:

- Bluetooth name: `Orion-a1b2`
- Device id, used everywhere on the LAN: `orion-a1b2`
- Display name: `Orion` until changed through `device_name`

## Discovery

The app runs four searches at once and merges them into one list, deduplicated by `device_id`. Every hit is confirmed with a real `GET /api/info` (400 ms timeout, up to 64 at once) before it is shown, and the source is shown as a small tag.

| Source | How | Tag |
|---|---|---|
| UDP beacon | listen on UDP 7332 | `beacon` |
| mDNS | query `_orion._tcp.local` | `mdns` |
| Sweep | every address in the /24 of up to three local IPv4 interfaces, the default route first | `sweep` |
| Names | resolve `orion.local` and `orion-<last4>.local` through the OS | `name` |
| Manual | the user types an address | `manual` |

mDNS is filtered by many routers and by Windows itself, which is why the beacon and the sweep exist. On a normal home network a board shows up within a few seconds.

### mDNS record

- Host name `orion` (so `orion.local`)
- Instance name: the device name
- Service `_orion._tcp`, port 80
- TXT: `id=<device_id>`, `name=<device name>`, `fw=<firmware version>`

### Beacon

While the board is on the network it broadcasts this every 2 seconds to `255.255.255.255:7332`:

```json
{ "orion": 1, "device_id": "orion-a1b2", "name": "Orion", "fw": "1.0.0", "ip": "192.168.1.40", "port": 80 }
```

## Tokens and auth

A paired app holds a random token, generated by the app (32 characters) and stored in the OS keychain. It sends the token on every request as `X-Orion-Token`, or as `?token=` in the query for things a browser or a WebSocket client fetches.

- The board keeps up to four tokens in NVS (`app_tokens`, newest first, comma separated), so a phone and a PC can both stay paired. Pairing again with a token already on the list moves it to the front; a fifth token pushes the oldest out.
- Every endpoint except `GET /api/info` needs a valid token. A missing or wrong token gets:

```
401 { "error": "unauthorized", "message": "missing or wrong X-Orion-Token" }
```

- A board with no paired app answers 401 to everything but `/api/info`. Its log says `no paired app: every request gets 401 until one pairs`.
- The factory reset on the board's menu erases every token along with everything else.

## Pairing

There are two ways in:

1. **Bluetooth setup** for a board that has no network yet (first start, after a reset, or after it moved). The app sends Wi-Fi, its token and optionally the model keys over an encrypted Bluetooth session.
2. **Pairing with a code** over the LAN for a board that is already on the network: a second app, a reinstalled app, a PC after the phone. No Wi-Fi to type.

The board has no access point mode.

### Bluetooth setup mode

The board uses Espressif's Unified Provisioning (ESP-IDF `wifi_provisioning` over NimBLE, protocomm security version 1 with a proof of possession), so standard ESP provisioning libraries work. The app uses `esp_ble_prov_dart` on top of `universal_ble`.

When the board enters setup mode:

- It boots with no saved Wi-Fi.
- A saved network did not answer within 30 s of boot (the board moved).
- A new network sent with `POST /api/provision` did not answer within 30 s.
- The user tapped "Wi-Fi setup" (`إعداد الواي فاي`) on the board's menu.
- `prov start` on the serial console.

Setup mode is a boot mode. Entering it from a running board writes `prov_boot=1` to NVS and restarts. On that boot the camera, wake word, audio and cloud never start, so Bluetooth has the whole heap. On success the boot continues into the normal system with the Wi-Fi the phone just set up, with no second restart. Setup mode ends on success, on `prov stop`, or after 10 minutes. Outside setup mode the Bluetooth controller's memory is released at boot and Bluetooth is off.

While in setup mode:

- The board advertises as `Orion-<last4>` with protocomm's default service UUID `021a9004-0382-4aea-bff4-6b3f1c5adfb4`.
- The screen shows the device name and a six digit code, drawn fresh every time setup mode starts. The code is the proof of possession. A wrong code fails the Security1 handshake; there is no separate error for it.
- The standard endpoints are there: `prov-session`, `prov-config`, `prov-scan`, `prov-ctrl`, `proto-ver` (characteristics 0xFF4F to 0xFF53).
- Two custom endpoints follow, in this order: `orion-pair` at 0xFF54 and `orion-config` at 0xFF55. Each also carries its name in the characteristic's user description, which is how `esp_prov` finds it.

Order the app follows:

1. Security1 session with the code.
2. `orion-pair`, as soon as the code is accepted:

```
request   { "app_token": "<8 to 64 chars>", "device_name": "Orion" }
response  { "device_id": "orion-a1b2", "ok": true }
```

   `device_name` is optional, up to 32 characters, default `Orion`. The response has no trailing NUL. The token and name are written to NVS at once, and the token joins the paired list.

3. Optionally `orion-config`, the same JSON as a `POST /api/config` body (see "POST /api/config"), so keys cross the encrypted session instead of the LAN. The response is the merged, masked config, or `{ "error": "invalid_config", "message": ... }`. A body longer than one write goes in parts:

```
request   { "part": 1, "parts": 3, "data": "<a slice of the JSON text>" }
response  { "ok": true, "part": 1 }        for every part but the last
          the merged, masked config          after the last part
```

   The app sends the whole body when it is 400 bytes or less, and otherwise slices of 150 characters, cut on characters so no UTF-8 sequence splits. A GATT value tops out at 512 bytes and JSON escaping can double a slice. The board gathers up to 4095 bytes.

4. `prov-scan`: the board scans and returns what it can see (SSID, signal, auth mode). The app shows this list because iOS cannot list Wi-Fi networks at all and Android restricts it. The board is 2.4 GHz only; 5 GHz networks never appear.
5. `prov-config` set and apply with SSID and password, then status polling:
   - Connected: status with the board's IP address. The password is written to NVS only now, from a RAM copy, so a wrong password never reaches flash.
   - Failed: reason "auth error" (wrong password) or "network not found". The board resets the manager and stays in setup mode on the same session, so the user can try another password without reconnecting. On some routers the wrong password verdict takes about 24 s, because the driver first reports a retryable "auth expired" and only the later 4-way handshake timeout is classified.
   - `attempts_remaining` is not sent (the driver retries until the reason is classified). The app times a join out after 45 s.
6. About 10 s after the station gets its address, Bluetooth stops by itself (`CONFIG_WIFI_PROV_AUTOSTOP_TIMEOUT`), the board releases the controller memory and starts the rest of the system. The app finds it on the LAN and confirms it with `/api/info`.

Measured on the board: Bluetooth up costs about 34 KB of internal RAM while it runs, and all of it comes back after release. A joining board reported connected about 7.5 s after the credentials.

### Pairing with a code

For a board already on the network.

```
POST /api/pair            no token
{ "app_token": "<8 to 64 chars>" }

202 { "ok": false, "error": "code_required", "expires_s": 120 }
```

The board shows a six digit code full screen for two minutes (a second request while it is up keeps the same code and reports the time left). The app asks the user for it and sends it with the same token:

```
POST /api/pair
{ "app_token": "...", "code": "482913" }

200 { "device_id": "orion-a1b2", "ok": true }
403 { "ok": false, "error": "bad_code", "left": 3, "message": "That is not the code on Orion's screen. 3 tries left." }
403 { "ok": false, "error": "bad_code", "left": 0, "message": "Five wrong codes. Ask Orion for a new one." }
403 { "ok": false, "error": "expired", "message": "That code timed out. Ask Orion for a new one." }
400 { "ok": false, "error": "bad_request", "message": "app_token 8 to 64 chars" }
503 { "ok": false, "error": "busy", "message": "could not save the pairing" }
```

Five wrong codes drop the code; asking again puts up a new one. A correct code takes it off the screen and adds the token to the paired list.

### Changing Wi-Fi

A paired app moves an online board to another network with:

```
POST /api/provision       token required
{ "wifi_ssid": "Home", "wifi_password": "...", "app_token": "...", "device_name": "Orion" }

200 { "device_id": "orion-a1b2", "ok": true }
400 { "error": "bad_request", "message": "wifi_ssid 1 to 32 chars, wifi_password up to 63, app_token 8 to 64" }
```

- `wifi_ssid` 1 to 32 characters, required. `wifi_password` up to 63, may be empty for an open network.
- `app_token` optional, 8 to 64 characters; when present it becomes the newest paired token. The app sends its current token, so it stays paired.
- `device_name` optional, 1 to 32.
- The body must be under 512 bytes.

The board stores the new network, switches to it, and arms the 30 s watch: if the new network never answers, it restarts into Bluetooth setup mode, where the app can finish the move while keeping its token.

## REST

All bodies are JSON. Errors look like `{ "error": "<code>", "message": "<human text>" }` unless noted. The HTTP server allows 8 open sockets (two linked apps with their WebSockets and keep-alive connections, plus the camera stream) and closes the least recently used when full.

### GET /api/info

No token. Used by discovery to confirm a board before the app holds a token.

```json
{
  "device_id": "orion-a1b2",
  "name": "Orion",
  "fw_version": "1.0.0",
  "hw": "t-cameraplus-s3",
  "ip": "192.168.1.40",
  "uptime_s": 1234,
  "has_camera": true,
  "config_version": 2,
  "providers": {
    "llm": ["openai_compatible"],
    "stt": ["fish", "openai_compatible"],
    "tts": ["fish", "openai_compatible"]
  },
  "source": "https://github.com/MultiX0"
}
```

`config_version` 2 means the board takes the separate `llm`, `stt` and `tts` blocks below. An app that meets a board without the field falls back to the older `llm` and `fish` blocks and says a non-Fish voice stage needs a firmware update. `source` is where the firmware comes from; the app ignores it.

### GET /api/state

```json
{
  "mode": "idle",
  "wifi_rssi": -52,
  "battery_pct": null,
  "volume": 70,
  "wake_word_enabled": true,
  "muted": false,
  "last_turn_id": "t_00042",
  "error": null
}
```

`mode` is one of `idle`, `listening`, `thinking`, `speaking`, `error`, `offline`. The board's internal states map onto it like this:

| Board state | `mode` |
|---|---|
| boot, offline | `offline` |
| idle | `idle` |
| wake, listening | `listening` |
| thinking | `thinking` |
| speaking | `speaking` |
| error | `error` |

`battery_pct` is always `null` (the board runs on USB) and `muted` always `false` in this firmware. `wake_word_enabled` is the stored setting. `volume` is the stored volume, 0 to 100.

### GET /api/config

The whole config with secrets masked: an `api_key` or `pc.token` reads `"...4f2a"` (the last four characters) or `null` when none is stored.

```json
{
  "device_name": "Orion",
  "volume": 70,
  "wake_word_enabled": true,
  "time_zone": "<+03>-3",
  "llm": {
    "provider": "deepinfra",
    "base_url": "https://api.deepinfra.com/v1/openai",
    "api_key": "...4f2a",
    "model": "google/gemma-4-31B-it-turbo"
  },
  "stt": {
    "provider": "fish",
    "base_url": null,
    "api_key": "...9c1d",
    "model": "transcribe-1"
  },
  "tts": {
    "provider": "fish",
    "base_url": null,
    "api_key": "...9c1d",
    "model": "s2.1-pro-free",
    "voice": "9a68c1d739134940a4297c996c5ca6a1"
  },
  "pc": {
    "enabled": false,
    "base_url": "",
    "token": null,
    "approval": "ask"
  }
}
```

`503 { "error": "not_ready", "message": "settings not loaded" }` if the settings component has not started.

### POST /api/config

A partial object, merged field by field onto the stored config. Nothing is stored unless every value passes. Answers the merged config, masked, exactly as `GET` does.

```
200  the merged, masked config
400  { "error": "invalid_config", "message": "stt.model: fish takes transcribe-1 or transcribe-1-pro" }
503  { "error": "store_failed", "message": "could not store the config" }
```

The body must be 1 to 4095 bytes.

Fields and rules:

| Field | Rule |
|---|---|
| `device_name` | string, 1 to 32 characters |
| `volume` | integer 0 to 100. Applies to the speaker at once. |
| `wake_word_enabled` | true or false. Applies at once: off stops the wake word listener, and a tap on the screen, the side button or the app still starts a turn. |
| `time_zone` | a POSIX TZ string under 48 characters, only letters, digits and `<>+-:,./`, such as `UTC0`, `<+03>-3` or `<+0530>-5:30`. Applies to the clock at once. The apps send a fixed offset read from their own clock, and send it again when summer time moves it. |
| `llm.provider` | a label the app shows: `deepinfra`, `openai`, `anthropic`, `groq`, `openrouter`, `ollama`, `custom`. The board only uses `base_url`, `api_key` and `model`. |
| `stt.provider`, `tts.provider` | `fish` or `openai_compatible` |
| `*.base_url` | up to 128 characters. Must start with `http://` or `https://` unless the provider is `fish`, where it is ignored. `null` clears. |
| `*.api_key` | up to 200 characters. Omitted keeps the stored key, `""` or `null` clears it, anything else replaces it. |
| `*.model` | 1 to 96 characters. With `stt.provider` `fish` it must be `transcribe-1` or `transcribe-1-pro`. |
| `tts.voice` | up to 64 characters, and there must be a voice after the merge. For Fish it is a voice model id, sent as `reference_id`. |
| `pc.enabled` | true or false. `true` needs a `pc.base_url` that starts with `http://` or `https://`. |
| `pc.base_url` | the PC brain, like `http://192.168.1.20:7331` |
| `pc.token` | up to 64 characters, the token the board sends to the PC brain |
| `pc.approval` | `ask` or `auto`, default `ask` |

Any string value with a quote, a backslash or a control character is refused.

What each stage means on the board:

- **Language model.** OpenAI chat completions with streaming, `POST <base_url>/chat/completions`, bearer key. `http://` is allowed, for Ollama or another server on the LAN. `localhost` would mean the board itself, so the app sends the PC's LAN address instead.
- **Speech to text, `fish`.** Fish Audio ASR, `https://api.fish.audio/v1/asr`, model in the `model` header. Streamed while the user is still talking. It bills Fish API credit, separate from the free text to speech.
- **Speech to text, `openai_compatible`.** One multipart `POST <base_url>/audio/transcriptions` with `file` and `model` after the user stops, for example DeepInfra `Qwen/Qwen3-ASR-1.7B`, Groq `whisper-large-v3-turbo` or OpenAI `gpt-4o-mini-transcribe`. No `language` field is ever sent: a language hint made Whisper translate English questions into Arabic.
- **Text to speech, `fish`.** Fish Audio `POST https://api.fish.audio/v1/tts` with `reference_id` set to the voice, `format: pcm`, `latency: balanced`, no `prosody` object. The board asks for 32 kHz.
- **Text to speech, `openai_compatible`.** `POST <base_url>/audio/speech` with `model`, `input`, `voice` and `response_format: "pcm"` (24 kHz, 16 bit, mono). Voice cues such as `[laugh]` only work on Fish, so the board leaves the tag rules out of the prompt, tells the model not to write brackets and strips any from the text. A 32 character hex voice (a Fish id left behind) is dropped, and a Fish model name left in `tts_model` is replaced with `Qwen/Qwen3-TTS`.

A changed block applies from the next turn, with no restart. The board rereads its settings and drops any kept-alive connection whose host changed. If a turn is running at that moment the reload waits for it and retries every second.

The defaults, which a new board and a factory reset both start from:

| Stage | Default |
|---|---|
| Language model | DeepInfra, `https://api.deepinfra.com/v1/openai`, `google/gemma-4-31B-it-turbo` |
| Speech to text | Fish Audio `transcribe-1` |
| Text to speech | Fish Audio `s2.1-pro-free`, Orion Voice `9a68c1d739134940a4297c996c5ca6a1` |
| PC | off, approval `ask` |

When `stt` and `tts` are both on Fish, one Fish key serves both. The app sends the same key in both blocks.

Older fields still accepted in a POST so older app builds keep working: `fish.api_key` (goes to `tts`, and to `stt` when it is on Fish), `fish.voice_id` and `fish.tts_model` (go to `tts`). `llm.system_prompt` is ignored.

### POST /api/config/test

```
{ "stage": "llm" | "stt" | "tts" }
```

The board makes the smallest real request with what it has stored: a one token completion, one second of silence transcribed, or two words synthesized into nothing.

```
200 { "ok": true, "ms": 412 }
200 { "ok": false, "error": "http_401", "message": "llm test failed after 380 ms" }
409 { "ok": false, "error": "busy", "message": "a turn is running" }
400 { "ok": false, "error": "invalid_stage", "message": "stage is llm, stt or tts" }
```

`error` is `http_<status>`, `timeout`, `bad_response` or `unreachable`. A Fish 402 means the account has no API credit, and the app says so in those words. On a 409 the app shows "Orion is talking, trying again" and retries every 2 s. The app sends a stage's block first if it changed, because the board tests what it has stored.

### POST /api/talk

Start a turn from the app. Only accepted while the board is idle.

```
{}                       listen now, as if the button was pressed
{ "text": "..." }        skip the microphone and run the turn on this text

200 { "turn_id": "t_00043" }
409 { "error": "busy", "message": "Orion is in the middle of a turn" }
400 { "error": "bad_request", "message": "body must be JSON" }
```

The body may be empty. Progress arrives over the WebSocket. There is no "stop listening" call: the board ends the recording itself after about 600 ms of silence.

### POST /api/talk/snapshot

The same, but the board takes a picture first and sends it to the model with the text. Used by "Ask about this" on the app's camera screen. Without `text` the question is "What is in front of you?".

### POST /api/say

```
{ "text": "Dinner is ready." }

200 { "ok": true }
400 { "error": "bad_request", "message": "text is required" }
409 { "error": "busy", ... }
```

The board speaks the text through its text to speech, no model. The screen and the WebSocket follow it like a reply: thinking until the first audio, then speaking, then idle.

### POST /api/stop

Cancels whatever the board is doing (listening, thinking or speaking) and returns to idle. Always `200 { "ok": true }`.

### GET /api/history?limit=20&before=t_00040

The board keeps its last 40 turns in PSRAM. They are lost on a restart.

```json
{
  "turns": [
    {
      "id": "t_00042",
      "started_at": "2026-01-02T21:10:03Z",
      "transcript": "what's on my desk",
      "reply": "A keyboard, a mug and a very tired cat.",
      "had_image": true,
      "tool_calls": [],
      "timings_ms": { "total": 5200 }
    }
  ],
  "next_before": "t_00022"
}
```

- `limit` 1 to 40, default 20. `before` returns turns older than that id.
- Newest first. A turn where nobody said anything and nothing was answered is left out.
- `had_image` is true for turns started with `/api/talk/snapshot`.
- `tool_calls` is always empty on the board, and `timings_ms` carries only `total`. The PC brain keeps its own record of what it did; see [HARNESS.md](HARNESS.md).
- `next_before` is `null` when there is nothing older.

### GET /capture

One JPEG, `image/jpeg`, 640x480, quality 12 (roughly 9 to 31 KB depending on light). `409` while a stream is running, `503 { "error": "camera", ... }` if the capture fails.

### GET /stream

`multipart/x-mixed-replace; boundary=frame`. Each part is:

```
--frame
Content-Type: image/jpeg
Content-Length: 23017

<jpeg>
```

640x480 JPEG frames as fast as the camera gives them, around 10 to 12 per second. Up to two viewers share each captured frame, so a phone and a PC can watch at once; a third gets `409 { "error": "busy", "message": "two viewers already" }`. The token may be in the query (`/stream?token=...`). The stream runs on its own task so the HTTP server keeps answering. The app closes the stream when the camera screen is not visible.

The app's parser accepts any boundary token, `Content-Length` present or absent, and CRLF or bare LF between headers, and reads each frame's width and height from the JPEG SOF marker. It retries a 409 every 2 s while the screen is open and reconnects with backoff when the socket drops.

### POST /api/restart

`200 { "ok": true }`, then the board restarts about 300 ms later. The app expects its WebSocket to drop and reconnects.

## WebSocket /ws

```
ws://<board>/ws?token=<app token>&client=pc|phone&brain=<host>:<port>
```

- `token` is required. A bad token gets `{ "type": "error", "code": "unauthorized", "message": "bad token" }` and the socket is closed.
- On connect the board sends a full `state` event, then events as they happen.
- The client may send `{ "type": "ping" }` and gets `{ "type": "pong" }`. Any frame counts as a sign of life.
- Query values are URL-decoded by the board. Dart encodes the colon in `host:port`.

### Links

`client=pc` or `client=phone` makes the socket a link. The board shows a dot for each app on its idle screen, lit while the link holds, and dims it the moment the socket closes or after 15 s without a frame. The apps ping every 5 s. Up to four links are tracked.

`brain=<host>:<port>`, from a phone only, offers the phone's own brain: the same OpenAI style endpoint as the PC's. The board then calls it with `Authorization: Bearer <that phone's app token>` while the link lasts. See "Board to brain".

A PC that links is checked straight away (its health check runs at once), so it answers the very next turn.

### Events

Every event has `type` and `ts` (UTC, ISO 8601, from SNTP). `turn_id` is `t_` and a five digit counter that starts again at every boot.

```json
{ "type": "state", "ts": "...", "mode": "listening", "wifi_rssi": -50, "battery_pct": null, "volume": 70, "wake_word_enabled": true, "muted": false, "last_turn_id": "t_00043", "error": null }
{ "type": "turn.start", "ts": "...", "turn_id": "t_00043", "source": "wake" }
{ "type": "turn.transcript", "ts": "...", "turn_id": "t_00043", "text": "what time is it" }
{ "type": "turn.reply", "ts": "...", "turn_id": "t_00043", "text": "It is ten past nine." }
{ "type": "tts.start", "ts": "...", "turn_id": "t_00043" }
{ "type": "tts.end", "ts": "...", "turn_id": "t_00043" }
{ "type": "turn.end", "ts": "...", "turn_id": "t_00043", "timings_ms": { "total": 4100 } }
```

- `state` carries the same fields as `GET /api/state` and is sent on every state change.
- `turn.start` fires when the board leaves idle. `source` is `app` or `app_snapshot` for the turn an app asked for, and `wake` for everything else (the wake word, the button, a tap).
- `turn.transcript` is what the user said, `turn.reply` the full answer text with any emotion tags still in it. The reply can arrive after the first audio, since the answer is spoken while it is written.
- `tts.start` and `tts.end` bracket the speaking state.
- `turn.end` fires when the board is back to idle, with the total time.

The app's orb follows `state.mode` directly; the `turn.*` events feed the conversation and talk screens live, before `/api/history` is fetched again.

The app also understands `turn.tool` and `log` events, which the mock board sends. The firmware does not send them.

## Board to brain

With PC control on, or a phone linked with a `brain`, the board sends each turn to an extended brain instead of straight to its own model. The brain is the Orion app's tool server; see [HARNESS.md](HARNESS.md) for what it does with the turn.

Order for every turn: the PC (when `pc.enabled` and its last check passed), then a linked phone, then the board's own model. A brain that fails before a word has been spoken hands the same turn to the next one, and is marked down until its next check passes.

### Health check

```
GET <brain>/tools
Authorization: Bearer <token>
```

A 200 within 3 s means the brain is up. The board checks the PC on every prewarm, which happens at the wake word and every 40 s while idle (the same heartbeat keeps the cloud connections warm). A phone is taken as up the moment it links, and rechecked the same way after a failure. The board's menu PC card shows the result.

The response is the tool list in OpenAI function format, `{ "tools": [ { "type": "function", "function": { ... } }, ... ] }`. The board does not use the list itself; the brain runs its own tools.

### The turn

```
POST <brain>/v1/chat/completions
Authorization: Bearer <token>
Content-Type: application/json

{ "model": "...", "stream": true, "max_tokens": 200, "temperature": 0.6,
  "messages": [ system, ...history, user ], "tools": [ look ] }
```

The same request the board would send its own model: the system prompt with the local date and time, the last few turns, the question, and the board's own `look` tool (its camera). The brain answers with OpenAI SSE, `data: {"choices":[{"delta":{"content":"..."}}]}` lines and `data: [DONE]`. If the brain wants the camera it streams a `look` tool call, the board takes a picture and sends a second request with the image.

A brain that cannot answer at all (no model set up on that PC, a bad key, no internet) must answer before streaming, with a non-200 status such as 503. The board then answers with its own model.

Rules a brain's stream has to keep, each learned from a failure on the board:

- **Open with an empty event.** `data: {"choices":[{"delta":{"role":"assistant","content":""}}]}` first. ESP-IDF's HTTP client keeps only the last body piece that arrives together with the headers; without the empty opener the first word was lost ("is eight eighteen").
- **Fill a whole read.** The board reads the stream 128 bytes at a time, and a read returns only when all 128 bytes are in or the stream ends. Anything shorter sits unread. A keep-alive is therefore an SSE comment padded to 128 bytes (`: working` and spaces, then a blank line), and one goes right after a spoken filler so the filler is read at once.
- **Show life every few seconds.** Any bytes read count as progress: the board's 30 s turn deadline counts from the last read, not from the wake word. A brain working through a task sends a keep-alive at least every 3 s.
- **Fillers of 15 letters or more.** The board's sentence chunker holds a first piece shorter than 15 speakable characters until more text arrives. "One moment, I'm on it." and "لحظة من فضلك، أعمل على ذلك." are long enough; "One moment." waited 30 s.
- **No control tokens.** Model control tokens such as `<turn|>` and `<|im_end|>` must not reach the voice. The PC brain drops them, and the board's chunker drops them again.

### The PC tool interface

The desktop tool server also serves a direct tool-call interface. The firmware does not use it (the brain runs tools itself), but the mock board, the tests and `tool/pc_harness.dart` do.

```
GET  /tools                    the catalog, as above
POST /tool                     { "call_id": "c1", "turn_id": "t_00043", "name": "open_app", "args": { "name": "spotify" }, "approval": "ask" }
GET  /tool/<call_id>           the current status of a call
GET  /ws                       { "type": "tool.update", "call_id": ..., "status": ..., "result": ... }
                               { "type": "agent.log", "job_id": ..., "text": ... }
```

`POST /tool` answers at once with one of:

```json
{ "status": "done", "result": "Opened Spotify" }
{ "status": "pending_confirmation", "confirm_id": "kc1" }
{ "status": "running", "job_id": "j3" }
{ "status": "error", "message": "denied by user" }
```

Every endpoint takes the pairing token as `X-Orion-Token`, as a bearer, or as `?token=`. With no token paired yet, the server refuses everything with 401.

## The mock board

```
dart run tool/mock_device/main.dart [--port 8080] [--fps 10] [--flaky] [--config-v1]
```

It serves everything above from memory, beacons on UDP 7332 with each of the host's IPv4 addresses, and streams the JPEGs in `tool/mock_device/frames/`.

- `POST /api/talk` walks a scripted turn: listening, thinking, then speaking, with the right events and a canned transcript and reply. With `pc.enabled` it calls the desktop's `POST /tool` for real on some turns and reports each status as a `turn.tool` event.
- Saying "ask me first" or "act on your own" in a typed turn changes `pc.approval`, so the approval switch can be tried by voice. The real board does not do this.
- The pairing code is always `123456`.
- Keys it scripts for `POST /api/config/test`: `bad` answers `http_401`, `nocredit` as the Fish speech to text key answers `http_402`, `busy` answers 409.
- `--config-v1` makes it an older board without `config_version`.
- `--flaky` drops every WebSocket every 20 s to exercise reconnects.
- Until something pairs, it answers without a token. It keeps a single token, set by `POST /api/pair` or `POST /api/provision`, so the last app to pair replaces the one before: one phone or one PC per mock at a time.
- Its `turn.start` says `button` for a plain `POST /api/talk`, where the board says `wake`.

`flutter run -d windows --dart-define=ORION_FAKE_BLE=true` walks the whole Bluetooth setup against a scripted board: code `123456`, the password `wrongpass` fails, the hidden network `Observatory` joins, any other unknown name is not found. It reports `localhost:8080` as its address, so the flow ends paired with the mock.
